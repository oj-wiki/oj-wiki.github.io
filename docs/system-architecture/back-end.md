# 后端

后端是 OJ 的业务核心：它接收浏览器请求，验证身份与权限，读写业务数据，并把需要执行的提交交给评测队列。评测代码不应在 Web 请求进程中运行；后端负责协调业务状态，评测机负责隔离执行，两者通过有认证的内部接口或消息队列通信。

## 数据库中的主要数据

数据库适合保存需要查询、关联和事务更新的结构化信息。常见实体包括：

- **用户与权限**：账号、资料、角色、团队成员关系，以及用户在课程、题库或比赛中的授权。
- **题目与版本**：题面、限制、标签、语言配置、测试点分组、checker 设置等元数据。较大的测试文件和附件通常保存在文件存储中，数据库保存其标识、版本和摘要。
- **比赛**：起止时间、赛制、参赛队伍、题目集合、公告与澄清，以及封榜等显示规则。
- **提交与评测**：提交者、题目/比赛、代码文件位置、创建时间、当前状态、测试点结果、分数、耗时和内存统计。
- **操作记录**：重测、改题、改分、权限变更等管理操作的执行人、时间、原因和影响范围。

这些实体之间需要稳定的 ID 和明确的关联关系。例如，提交应引用提交时使用的题目及评测配置版本；否则题目后来被修改后，旧提交可能无法复现。源码、答案和测试数据不宜作为超大字段直接塞进普通业务表，通常由文件或对象存储管理，再由后端实施授权访问。

## 系统配置

系统配置包括数据库和文件存储连接、邮件服务、公开站点地址、默认语言与编译器、评测节点地址、队列参数、上传限制、会话策略和功能开关等。应区分三类配置：

1. **部署密钥**：数据库密码、签名密钥、评测端凭据等，通过秘密管理或受限环境变量注入，不进入代码仓库、客户端响应和普通日志。
2. **运维配置**：服务地址、队列容量、超时和上传上限等，由部署环境维护并在启动时校验；缺少必要配置时应明确失败，避免以不安全默认值继续运行。
3. **业务配置**：题目、比赛、编译语言和赛制规则等，由有权限的管理员通过界面管理，并保存修改记录或版本。

集群中的服务实例应使用一致的业务配置版本。修改评测语言或队列路由时，还需考虑正在排队和运行的任务如何处理，避免新旧配置混用。

## 面向前端的 API

前端 API 负责认证并暴露题目、提交、比赛、排行榜和管理能力。后端不能只依赖前端隐藏按钮或表单校验：每次请求都要检查用户是否有权访问目标题目、提交、队伍或管理操作，并校验字段、文件大小、速率和状态转换。

接口应明确请求/响应格式、错误码、分页与排序规则。提交接口成功时，应返回稳定的提交 ID 和初始状态；页面随后可轮询或订阅状态变化。涉及创建提交、报名或发布公告的请求需要考虑重复发送，例如通过幂等键避免网络重试造成重复操作。对题面、公告和编译输出等用户可控内容，应按上下文安全编码后再展示。

## 与评测机的接口

后端或调度器向评测机分配任务时，任务至少需要能关联提交 ID、题目版本、代码和数据的位置、语言/编译参数、资源限制及任务版本。评测机只应获得执行当前任务必需的文件和权限，不应直接访问业务数据库或获得云存储的广泛凭据。

评测机回传的结果通常包括任务标识、总状态、测试点结果、分数、时间/内存统计和诊断信息。后端应验证来源、任务是否仍有效、状态转换是否合法及结果格式是否符合限制；超长日志和任意路径不能直接作为可信数据处理。详细的领取、重试和取消语义见[评测队列](queue.md)，执行边界见[评测机](judger.md)。

## 提交状态与可靠性

一条提交记录通常经历“已提交/等待 → 编译中 → 评测中 → 完成”，也可能进入取消或内部错误状态。状态变更应有明确的合法转换；终态结果需要与使用的任务版本绑定，防止较早的重测结果覆盖较新的结果。

提交写入数据库和投递队列是两个独立操作，进程可能在两者之间崩溃。可使用事务性 outbox 等模式记录待投递事件，并由后台发送器重试；队列消费者和结果回调则按任务 ID 幂等处理，以承受重复投递。失败重试应区分可恢复的基础设施故障与正常评测结果（如 WA、TLE），并设置次数和退避上限。

后端实例尽量保持无状态，以便水平扩展；需要共享的会话和任务状态放入合适的共享存储。备份要覆盖数据库及其引用的持久文件，恢复演练应验证两者的关联仍然有效。总体提交链路见[系统架构](index.md)，数据边界见[数据存储](storage.md)。
