# 代码执行

在用户提交代码之后，需要在一个安全，受信任，一致的环境中编译，并执行用户的代码。代码执行需要满足

- 环境一致：避免运行环境对结果的影响。理想情况下，运行硬件和软件需要保持一致。
- 环境隔离：用户程序可能包含恶意代码，需要保证不会修改或者破坏环境，窃取机密信息
- 资源限制：用户程序需要在题目给定的 CPU ，内存等限制下运行
- 资源统计：用户程序运行结束后，需要统计使用的系统资源
- 文件收集：需要在执行前准备输入文件，并在执行后收集产生的输出文件

本文档以 Linux 评测机为主，也列出 macOS 与 Windows 可用的隔离边界。若评测不可信提交，通常应将 Linux 作为执行节点；其他系统的应用沙箱 API 不等同于容器或虚拟机，功能和威胁模型需要逐项验证。

## 环境一致

在分布式系统中，运行环境一致性可以通过固定版本的容器镜像或者虚拟机镜像实现，或者使用可复现的包管理（例如 Nix）。还应记录评测节点的 CPU 架构、内核、编译器/运行时版本、编译参数和环境变量。容器共享宿主机内核，镜像本身不提供安全边界；需要更强隔离时可考虑微型虚拟机或用户态内核。

## 环境隔离

- 网络访问限制
- 文件系统访问限制
- 特权操作限制

隔离应按层组合：独立低权限身份、最小化文件系统视图、关闭网络、限制系统调用和能力、再用内核资源控制器设定上限。编译器、checker、交互器和生成器同样可能处理不可信输入，也应限制资源并隔离运行。对沙箱升级或内核变化，应使用逃逸、fork 炸弹、超时和超量输出用例验证实际行为。

Linux 的常见边界分别由 [namespace](./namespace)、[cgroup](./control-group)、[seccomp](./seccomp) 与 [Landlock](./landlock) 等机制实现；它们各自负责不同范围，部署时应组合并验证。

## 资源限制

运行环境通常需要限制以下资源

- 时间限制
  - CPU 时间
  - 真实 （Wall-clock）时间
- 内存限制
  - 最大内存使用
  - 最大虚拟内存
  - 最大栈空间使用
- 输出限制
- 文件大小限制
- 进程数量限制
- 打开的文件描述符及临时磁盘空间

## 资源统计

运行结束以后需要统计使用的计算资源

- CPU 时间
- 真实（Wall-clock）时间
- 最大内存使用量
- 进程树的 CPU/内存统计与 OOM、超时原因

不要把虚拟内存、RSS、cgroup 内存计量和语言运行时报告的内存视为同一口径。评测结果应记录原始计量及限制来源，平台再映射为 MLE/TLE 等状态。

## 文件收集

运行结束时，可能需要收集产生的结果文件。如编译之后的可执行文件，或者运行时写入的答案文件。需要确认

- 文件存在
- 文件大小符合限制
- 文件是一个普通文件（不是文件夹，设备，管道等）
- 文件路径没有越出工作目录，并处理符号链接、硬链接和检查后的竞态条件
